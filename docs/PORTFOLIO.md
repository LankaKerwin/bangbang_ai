# 枪豆人 AI：让 Agent 在真实游戏里学会"活着并变强"

> 一个从「屏幕像素」到「会自己打 Boss」的完整闭环作品集项目。
> 技术栈：YOLO 目标检测 · 分层感知(159 维状态) · PPO 强化学习 · 人类示范行为克隆(BC) · OCR · 虚拟手柄注入

**一句话亮点**：不用读游戏内存、不碰官方 API，Agent 只靠「看屏幕 + 模拟手柄」在一个真实、实时、有弹幕的竞技游戏里从零学会生存与击杀——感知、决策、执行全部自己闭环。

GitHub：https://github.com/LankaKerwin/bangbang_ai

## 1. 项目是什么

- 游戏：Steam《枪豆人 Bang Bang Barrage》（Unity IL2CPP，无法读内存辅助）
- 锁定配置：角色小草(6 血)、武器霰弹枪(3 发半自动)、模式 简单·无限（Boss 无限循环随机出现）
- 终极目标：训练出一个**超越脚本规则上限**的 AI 玩家——会躲弹幕、会控挡位连杀、会打 Boss
- 关键约束：游戏本体 1× 实时运行，RL 采样墙钟受限 → 逼着做**样本效率**的取舍

### 架构一览

```
屏幕(mss) ──▶ YOLO(敌人/障碍检测) + 血量/弹药/商店/公告OCR ──▶ 159维状态
                                                                      │
                                                          PPO / BC(行为克隆)
                                                                      │
                                                  输入层: 合成鼠标瞄准+左键点射+空格重开(vgamepad 退役, 见 §3.13) ◀──┘
```
*2026-09-07 决策：虚拟手柄绑定间歇失效 → 合成鼠标+空格，键鼠=真实设备路径。*

## 3. 每一环的「问题 → 解决 → 决策理由」（核心价值区）

### 3.1 为什么用 YOLO 分层感知，而不是把像素直接喂 RL？

- **问题**：像素端到端 RL 需要 10⁶~10⁷ 帧才能学会"看"+“决策”；本环境 1× 实时约 2 步/秒 → 100 万帧 = 一周以上，不可行
- **解决**：用 YOLO 预训练解决"视觉识别"，RL 只学 159 维上的"决策"，样本需求降 1-2 个数量级
- **代价与认知**：RL 上限受感知覆盖限制 → 所以感知层必须持续验收（见 §3.3）
- **决策**：感知分层的本质 = 把"看"与"想"解耦，视觉难题用监督学习解决，行为难题留给 RL

### 3.2 YOLO 训练的三个坑

1. **中文路径 cv2 静默失败** → 统一 `open + imdecode`（unicode 安全读取）
2. **小样本(60 张)mAP 虚高** → 数字只作参考，最终以**真实对战验收**为准（所有敌人可识别+跨帧跟踪）
3. **标注集要覆盖"部分出场"等稀有状态** → 迭代闭环：标→转→训→测→补

### 3.3 状态设计：159 维里到底有什么、为什么

- 敌情(YOLO 框) + **48 维弹幕危险栅格** + **48 维障碍栅格** + 伤害记忆(受伤时刻+朝向) + 血量/弹药 + 瞄准方向
- **关键决策**：MLP 无时序记忆 → 时序信息(弹幕飞向)要靠相邻帧运动特征表达 → 状态里显式带 prev 帧信息
- **验收方法**：先喂给规则脚本实测手感，再上 RL（状态好不好，脚本先当试金石）

### 3.4 死亡判定：不能读内存，怎么知道死了？

- 玩家船消失连续 ≥6 帧 **且** 血量==0（颜色无关，双条件防误报）
- 踩坑：死亡画面世界仍在动（弹幕继续）→ 不能用"画面冻结"当死亡信号；用「无船+无血」组合
- 死亡后自动重开：长按 A 跳过加载 + 逐秒验证血量直到回来（无人值守的关键）

### 3.5 时间加速的完整否决史（RL 采样天花板）

- 试过 Cheat Engine 8×：只加速菜单/UI/音效，**不加速战斗实体** → 无效
- 时间缩放 patch：风险高收益不确定 → 搁置
- 虚拟机/云 GPU：计算墙钟上限不变，仅 UI 时钟变快 → 全部否决
- **结论写进认知**：样本/秒 = 算力 ÷ 每步成本，任何时钟/虚拟化技巧都无法绕过 → 优化只能做「降每步成本 + 加采样密度」

### 3.6 PPO 冒烟：fps=2 是怎么抠出来的

- 最初每步 0.1s 理论，实测 2 步/秒 —— 感知(YOLO+栅格) ~0.3-0.5s/步是瓶颈
- 中途存档(每 2048 步)、Monitor 回合统计、--resume 续训 → 长跑不怕断
- **诊断工具**：每局死亡打印"存活 N 步 / 秒"探针 → 区分「reset 日志密集是错觉」与「真快速死亡」

### 3.7 击杀奖励：右上角分数 OCR 的连环坑

1. **看错颜色**：初判"黄色"，像素统计证明是**白色**(R≈G≈B) → 一切以数据为准，别信预览图
2. **RapidOCR 对小 ROI 识别差**：检测模型把 `9,960` 切碎成单字符 → 改 **use_det=False 整行识别**，先放大到 ~640px → 三张校准图全对
3. **性能**：每步 2 遍 OCR → fps 从 2 掉到 1 → 优化「正色读出就不跑反色 + 分数每 5 步采样一次(分数单调，Δ累计不变)」→ fps 回到 2
4. **防误报**：死亡结算时 Boss/钻石分暴涨 → 死亡帧屏蔽分数奖励；读数只信"涨"的，抖动回退丢弃
5. **奖励校准**：挡位单杀分(白60/蓝180/黄360/红600) → k=0.005/分 → 单杀奖励 0.3~3.0，**分数越高奖励越多**，天然鼓励冲高挡

### 3.8 Boss 击杀奖励：奖励时间公告

- Boss 击杀**结算才加分** → 实时分数 OCR 捕捉不到 → 改用中央大字「奖励时间」公告当事件信号
- **公告颜色会变**(样例粉色) → 禁止颜色模板 → 直接彩色 OCR 读文本
- 坑：大字超大时**放大反而切碎**成"劲时间、励" → 缩小到识别模型舒适尺度(0.5/0.3/0.18 全部可读)
- 一次性 +50(=结算 10000 分等值)，active 锁防重复

### 3.9 摇杆疑云：差点推翻整个训练方向

- 真人瞄准用左摇杆，代码注入却一直用右摇杆 → **怀疑右摇杆无效、之前训练全废**
- 实测：游戏**双摇杆等效** → 虚惊，训练没废
- 教训：硬件映射假设必须实测验证，一个想当然可以毁掉一周训练
- 决策：统一注入左摇杆，与真人录制**字面一致**

### 3.10 为什么做人类示范 BC 而不是直接长跑 RL

- RL 从零探索极慢；BC 用"老师示范"跳过最慢的摸索期
- 为什么不用脚本当老师：脚本只会糙打(不躲弹) → 老师水平 = BC 上限
- **人类示范是最强老师**：会躲弹/会保连击/会打 Boss
- 录制器设计：旁观式(不注入虚拟手柄) + 与 env 同构的动作(左摇杆+RT) + **过滤死亡/结算/商店帧**(那些不是战斗决策)
- 链路：示范 → BC → PPO 微调(已支持 --resume 加载 BC 模型)

### 3.11 自驱动陷阱：BC 灵敏度假象（本会话最重要发现）

- 特征里加"距上次开火意图秒数(fire_since)"做时序上下文 → **离线(教师强制)评测灵敏度 94%，部署(自驱动)后崩到 0.04%**
- 原因：该特征由**教师动作**衍生，离线时泄漏"下一步该不该开枪"，模型没学会真判别；部署时模型自己产生的动作喂回自己 → 死锁
- 教训：**任何"由动作衍生"的输入都是泄漏**；验证 BC 必须自驱动(exp_selfdrive.py)，不能只看教师强制
- 决策：弃用 fire_since → 159 维纯外部特征 + 让 PPO 用奖励学开火时机

### 3.12 真实射程与开火时机的认知（159 维天花板）

- 弹药弧半径×1.1 当"可攻击距离"低估了 3 倍 → 真实射程≈3×弹药弧半径（实测人类开火帧 31% 被误判为"没目标"）
- 外推目标特征(ext, 3维)无判别力：听雨对目标开枪时偏差 7° vs 不开枪 9° → **单帧外部特征能解释的开火≈27-30%**
- 结论：**开火决策本质在时序/内部节律**（听雨≈0.5次/s 的节奏），单帧观测救不了 → 交给带记忆的 PPO + 时序奖励

### 3.13 输入设备：从虚拟手柄到合成鼠标（下一步主线）

- vgamepad(ViGEm) 绑定**间歇失效**（与蓝牙手柄插拔、槽位竞争、游戏识别时机都有关），非算法问题但卡死一切训练价值
- 听雨实测定案：键鼠玩只需要**鼠标移动(瞄准) + 左键(每点一枪)**；**空格=确认/跳(重开)，键盘A无效**；重开界面键鼠/手柄命令都收
- 决策：输入层改 **ctypes 合成鼠标+键盘空格**，vg 彻底退役 → 绑定问题从根上消失（键鼠是真实设备路径）
- 关键坑预案：**开枪有后坐力把船往反方向推** → 每次开火后要补偿/重新校准瞄准

## 4. 奖励设计哲学（v1 定稿）

```
存活 +0.0005/步     → 活着本身有微弱正反馈(调小: 纯分数导向, 防"活着白嫖")
掉血 -1.0/心, 死亡 -3.0 → 死亡有"掉心×6"自然兜底, 温和罚不压制冲分
击杀 = 涨分 × 0.005   → 分数为王: 自动包含"活得久/挡位高/杀得多"
                        (白60/蓝180/黄360/红600 → 单杀 0.3/0.9/1.8/3.0)
Boss 击杀(奖励时间公告) +50 → 一次性大信号, 不等结算
```

**原则**：能用分数表达的目标不单独设计奖励 → 减少 reward hacking 面；大事件(死亡/Boss)单独显式建模。
*注：早期 v0 用 存活+0.001 / 死亡-5.0，v1 定稿为上面数值（更纯的分数导向）。*

## 5. 问题速查表（复用价值最高的一页）

| 问题 | 一句话解法 |
|---|---|
| 中文路径 cv2.imwrite 失败 | imencode + open 二进制写 |
| RapidOCR 小字切碎 | use_det=False 整行识别 |
| OCR 大字读不好 | 缩小到 rec 尺度，别放大 |
| 死亡信号(无内存) | 无船≥6帧 AND 无血 |
| CE 时间加速无效 | 只动 UI 时钟，战斗实体不动 |
| 分数奖励结算误报 | 死亡帧屏蔽 + 只信涨分 |
| 公告颜色会变 | OCR 文本替代颜色模板 |
| reset 日志密集像死循环 | 每局打印存活秒数探针 |
| RL 曲线不动的排查顺序 | 感知是否系统性缺失 → 奖励是否太稀 → 探索/预热 |
